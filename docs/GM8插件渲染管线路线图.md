## 0. 问题定性（为什么要做这件事）

### 0.1 排查结论

以游戏内计时器（步事件开始 → 绘制结束的墙钟时长）为口径的实测时间线：

| 插件版本 | 计时读数 | 归因 |
|---|---|---|
| 8-26 版（a3a77e3 + 79ffd4c） | ~20% | 基线：批与引擎绘制互不干扰，但绘制顺序错误（靠游戏内手工冲刷硬压） |
| 9-14 上午合批系列（594da62/07d1e25 + 326817f/7ef24fd） | 50%（简单场景 20%） | 合批自动冲刷 + 快照式原子化。每次 flush ≈ 130-150 次设备调用（其中约 130 次为可证明的空转）+ 批重开 192/768KB memset；频率 = 引擎绘制与批的交错次数 |
| 9-14 下午设备丢失系列 | 70-80% | 代码级无热路径新增；已修的 Present 强制 vsync 不在计时窗口内，待 A/B 排除场景漂移 |

### 0.2 结构性根因

GM8 引擎是**即时提交者**（每次绘制直接落设备调用），GMGraphic 是**延迟提交者**（绘制先攒批、择机提交）。两条独立提交流共享同一个 D3D9 设备，靠 43 槽设备钩作同步闩：任何引擎状态写入发生前先冲刷挂起批，以此保证批的绘制顺序与状态正确。

该闩的**正确性成立**（字面闭合不变式：批打开期间设备状态不可能变化），但**成本结构不合理**：交错频率高时，每次冲刷的 ~150 次设备调用 × 每帧数十至数百次交错，构成每帧毫秒级的纯开销。

【通俗地说】两个人同时在一块白板上画画：一个画一笔立即生效，另一个先在草稿上攒一段再誊写。为了保证草稿誊写时白板状态和攒稿时一致，现在每次别人落笔前都要把草稿誊写完、再把白板原样抄一遍——抄写本身比画的内容还贵。问题不是抄得太慢，而是"誊写时机被别人控制"这件事本身。

### 0.3 终局方向

将提交权统一：引擎绘制也被捕获进同一个帧内命令队列，帧尾按调用序一次性回放。提交者唯一化之后，"另一个提交流改变环境"在结构上不复存在，同步闩、冲刷、快照、恢复整体失去存在理由。该形态即 GMS2 官方批处理器的架构（已被同一引擎家族的商业产品验证）。

## 1. 目标与非目标

**目标**

1. 短期：现架构下单次冲刷成本降低约 5 倍（~150 → ~30 次设备调用），批重开去掉大内存清零。
2. 长期：单一提交流。引擎绘制与插件批在同一个帧内队列中按调用序回放，交错频率不再影响每帧成本。
3. 全程不改变任何 GML API 的可见语义；现有游戏代码零修改即可运行。

**非目标**

- 不追求"一帧合并成一个大 draw call"的合并率。批的粒度 = 同纹理页的连续绘制（GMS2 同款）；不同纹理的绘制各自成段、保序即可。
- 不做场景图、绘制排序器、GPU 剔除等上游优化。
- 不改 GM8 资源模型（图集由 GMGraphic 现有 texture_atlas 提供，引擎未入图集的原生资源按独立段原样记录）。

## 2. 阶段〇：地基收尾（前置条件）

任何重构不得叠加在未验证、未提交的改动之上。当前两仓库各压着一整批未提交工作（设备丢失恢复系列、Present 恒 IMMEDIATE 修复等）。

| 事项 | 内容 | 验收 |
|---|---|---|
| A/B 归因 | 混搭实验：新 gex+旧 GMGraphic.dll / 旧 gex+新 GMGraphic.dll，同房间同实例数，游戏内计时器读数对比 | 50→70-80 的增量归因到具体 DLL，或确认场景漂移 |
| 设备丢失实测 | 睡眠/锁屏唤醒、TDR、分辨率切换后：gpart 恢复、冻结 VB 行为、图集纹理完整 | 已知行为：粒子清空重发属预期；其余内容无缺漏 |
| 提交 | 两仓库分主题提交（设备丢失系列 / Present 修复 / 计划文档） | 干净的工作树 |

【通俗地说】先把手里的活验完落袋。盖新楼之前，旧楼的维修单要签字归档，否则出了问题分不清是新楼的锅还是旧楼的锅。

## 3. 桥梁期：三件套（约 1 周）

> 本期三件互相独立、各自可单独实测与回退。它们同时是统一流的直接前置件：③ 的影子表被捕获器原样征用，① 的"自碰清单"是批段头机制的雏形。

### 3.1 修复②：去除批重开的大内存清零

**技术描述**：`vertex::begin` 当前每次批打开 memset 整个顶点缓冲（图集路径 8192×24B=192KB，ext 路径 8192×96B=768KB）。被绘制的顶点全部由 `add()`/`push_vertex_2d()` 全字段写入，绘制仅读取 `vbuff_c` 以内的顶点；memset 的唯一必要用途是 `!vbuff_use_struct` 时 count+1 语义下当前未完成顶点的清零。改为仅清零单个顶点槽（24/96 字节）。

**语义收窄（已知情，需记档）**：ext 顶点格式下，`d3d_vertex_ext_tex` 未写入的 uv stage（1-7）从"保证为 0"变为"未定义"。仅影响自定义 shader 采样未写入 TEXCOORD 通道的场景；GMS2 对同类 API 亦是"未写即未定义"契约。

**验收**：现网场景回归 + 计时器读数无回退。

### 3.2 修复③：设备状态影子表

**技术描述**：在 43 槽设备钩内同步维护一份状态影子（内存副本），覆盖引擎实际使用的状态闭包——IDA 已核定的 ~24 个 SetRenderState 站点、纹理/TSS/采样、三矩阵、FVF/声明/VS/PS、视口。此后插件内一切"需要知道当前设备状态"的场合（捕获器、SetVertexShader 包装、快照对照）读影子，不再调用设备的 Get* 接口（消除每次 Get 的运行时开销与 COM AddRef/Release 往返）。设备 Reset/重建后影子失效重建（挂接既有 reset 回调）。

附对账调试模式：影子 vs 真 Get 逐项比对，验证期开启，跑全场景零差异后转常规关闭。

【通俗地说】给设备的所有开关记一本账。以前每次想知道某个开关的状态都要跑去设备本人那里问一遍（还要签名登记）；现在翻自己的账本。这本账以后就是捕获器的唯一状态来源。

**验收**：对账模式全场景零差异；ps-only 场景引擎绘制正确（透传 VS 的 WVP 刷新走影子）。

### 3.3 修复①：批冲刷最小自愈

**技术描述**：`atlas::start_draw/end_draw` 的状态往返从三轮 38 项全量快照（114 次调用）改为"自碰清单"——捕获 end_draw 实际会触碰的状态（stage0-7 纹理、TSS ADDRESSU/V、COLOROP/COLORARG、PS/VS/声明，约 15 项），提交后按清单精确归还。三轮中的 `capture(now)` 与 `apply(g_batch_snap)` 在 43 槽字面闭合不变式下为可证明的空操作，直接删除。

**保留**：全量快照降级为调试对照开关（见 §6 脚手架），怀疑状态污染时一键切回比对。

**验收**：历史问题单全过——rTitle 入场幕帘顺序、psDissolution uniform、地图图标 d3d_transform、texture_repeat 平铺；双模式截图逐像素对比一致。

## 4. 统一流·阶段一：引擎绘制捕获器（约 2-3 周）

**技术描述**：

1. **捕获点唯一性**：8.0 引擎全部图元经 `DrawPrimitiveUP` 提交（全模块扫描核定，无 DrawPrimitive/IndexUP 站点），捕获面单一。
2. **段结构**：`{ 图元类型, 顶点数据副本(记录时 memcpy), 步长, 纹理(记录时 AddRef), 状态指纹(读影子表：FVF→声明映射、混合渲染态、TSS/采样、三矩阵、雾/Z 状态) }`。
3. **屏障类调用同队列**：`Clear`、`SetRenderTarget`、`SetDepthStencilSurface`、纹理内容更新（`UpdateTexture` 等）作为队列屏障记录，回放时原样执行——surface_set_target 与运行时烧图集天然保序。
4. **读回屏障**：`GetRenderTargetData`/`GetFrontBufferData`/锁定读回类操作触发"回放到此为止"，强制队列前段先落设备再执行读回。**[待定 Q1]** 第一版是否直接对读回函数报错/绕过（游戏内截图功能走旧路径），以回避最复杂的时序。
5. **生命周期**：队列对纹理等 COM 对象记录时 AddRef、回放后 Release——`texture_swap`、运行时删除资源等边角自然正确。
6. **不合并**：第一阶段同状态相邻段不做合并（不同纹理的段各自独立提交，GMS2 同款常态），合并作为后续优化。

【通俗地说】引擎每次落笔不再直接上白板，而是被拍成一张"操作卡"（画了什么点、用什么笔、蘸什么颜色）按顺序码进盒子里。白板从此只有一个人能碰。

## 5. 统一流·阶段二：回放器（约 2-3 周）

**技术描述**：

1. **回放点**：`EndScene` 钩子按调用序遍历队列：逐段应用状态 diff（对比前段指纹，只写变化项）、图集/SDF 段走现有提交代码（状态取自记录值，即批段头）、引擎段按记录状态提交。
2. **帧首确定性**：回放前将设备置入已知基准态，之后一切状态由队列主导——设备环境不再有"继承"概念。
3. **与既有机体的衔接**：gpart 的 RT ping-pong 即屏障序列，原样保序；设备丢失/Reset 时队列整体作废、下帧重录（挂接既有 reset 回调）；43 槽钩的 `fire_flush` 退役为"封段"（纯记账，零设备调用），冲刷风暴自机制上消失。
4. **影子表同步**：回放期间钩子照常维护影子（回放写入亦经 vtable），帧间一致性自动成立。

【通俗地说】帧尾由一个专职誊写员把盒子里的操作卡按顺序全部执行。因为整帧只有他碰白板，"画的时候白板是什么状态"不再是问题——每张卡自己写着呢。

## 6. 脚手架与收尾

- **模式开关**：GML 可调 `gmdx9_set_capture_mode(0/1)`（开发/验证期），一键在"现管线"与"统一流"间切换，用于截图对比、计时器对比、异常二分。**性质为带删除期限的脚手架，非永久特性**。
- **灰度**：以 gex 版本为单位（新版稳定跑一个版本 → 切默认），不做运行时灰度。
- **退役提交**：统一流默认并稳定后，专门一个提交删除旧提交路径，开关降级为无操作。用户侧回退手段 = 装回上一版 gex（文档明示），不以常驻双管线作保险。
- **[待定 Q2]** 旧路径删除时限：默认切换后 1 个版本还是 2 个版本。

## 8. 风险清单与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 3D 路径边角（灯光/雾/point sprite/模型）组合行为 | 捕获-回放观感差异 | 状态指纹全量覆盖（影子表按钩子实测范围收）；3D 测试场景先行 |
| 读回屏障时序 | 截图/像素读回结果错误 | **[待定 Q1]** 第一版将读回类绕过或报错；屏障机制二版补 |
| StateBlock / 第三方设备钩 | 既有契约盲区，影子与真实状态可能失同步 | 契约继承（文档明示"使用者自负"）；对账调试模式可检出失同步 |
| 大批量顶点 memcpy | 单次捕获开销 | UP 数据本就由运行时拷贝一次，捕获为第二次拷贝；量级实测后如必要改环形缓冲 |
| 队列内存 | 帧内驻留顶点副本 | 段顶点总量实测（预期 < 数 MB）；必要时复用环形顶点池 |
| 影子失同步引入的错误判定 | 花屏类偶发 | 对账模式 + 43 槽闭合不变式（与现架构同一信任基础，不新增信任面） |

## 9. 明确不做

- 不实现绘制排序/合并率优化（第一阶段保序即可，合并留作后续纯增益项）。
- 不动 D3D8 后端（无 GMDirectX9 时的原生路径维持现状）。
- 不新增 GML 面向用户的图形语义（仅新增开发期模式开关一个导出，随旧路径一并退役）。
- 不在统一流落地前引入 D3D9 StateBlock（作为最小自愈的可选实现评估过，跨驱动质量参差，通用插件保守起见不采用）。
