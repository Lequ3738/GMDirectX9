## 0. 问题定性（为什么要做这件事）

### 0.1 排查结论

以游戏内计时器（步事件开始 → 绘制结束的墙钟时长）为口径的实测时间线：

| 插件版本 | 计时读数 | 归因 |
|---|---|---|
| 8-26 版（a3a77e3 + 79ffd4c） | ~20% | 基线：批与引擎绘制互不干扰，但绘制顺序错误（靠游戏内手工冲刷硬压） |
| 9-14 上午合批系列（594da62/07d1e25 + 326817f/7ef24fd） | 50%（简单场景 20%） | 合批自动冲刷 + 快照式原子化。每次 flush ≈ 130-150 次设备调用（其中约 76 次为可证明的空转）+ 批重开 192/768KB memset；频率 = 引擎绘制与批的交错次数 |
| 9-14 下午设备丢失系列 | 70-80% | **已定案（实测定案 2026-09-14）**：元凶 = CreateDevice 的 interval 透传——runner 窗口化恒传 interval=0，D3D9 的 COPY+DEFAULT 是真阻塞垂直同步，透传即强制 vsync。恒 IMMEDIATE 修复后实测恢复正常 |

### 0.2 结构性根因

GM8 引擎是**即时提交者**（每次绘制直接落设备调用），GMGraphic 是**延迟提交者**（绘制先攒批、择机提交）。两条独立提交流共享同一个 D3D9 设备，靠 43 槽设备钩作同步闩：任何引擎状态写入发生前先冲刷挂起批，以此保证批的绘制顺序与状态正确。

该闩的**正确性成立**（字面闭合不变式：批打开期间设备状态不可能变化），但**成本结构不合理**：交错频率高时，每次冲刷的 ~150 次设备调用 × 每帧数十至数百次交错，构成每帧毫秒级的纯开销。

【通俗地说】两个人同时在一块白板上画画：一个画一笔立即生效，另一个先在草稿上攒一段再誊写。为了保证草稿誊写时白板状态和攒稿时一致，现在每次别人落笔前都要把草稿誊写完、再把白板原样抄一遍——抄写本身比画的内容还贵。问题不是抄得太慢，而是"誊写时机被别人控制"这件事本身。

### 0.3 终局方向

将提交权统一：引擎绘制也被捕获进同一个帧内命令队列，帧尾按调用序一次性回放。提交者唯一化之后，"另一个提交流改变环境"在结构上不复存在，同步闩、冲刷、快照、恢复整体失去存在理由。该形态即 GMS2 官方批处理器的架构（已被同一引擎家族的商业产品验证）。

## 1. 目标与非目标

**目标**

1. 短期：现架构下单次冲刷成本降低约 5 倍（~150 → ~30 次设备调用），批重开去掉大内存清零。✅ 已达成
2. 长期：单一提交流。引擎绘制与插件批在同一个帧内队列中按调用序回放，交错频率不再影响每帧成本。⏸ 挂起
3. 全程不改变任何 GML API 的可见语义；现有游戏代码零修改即可运行。✅ 全程遵守

**非目标**

- 不追求"一帧合并成一个大 draw call"的合并率。批的粒度 = 同纹理页的连续绘制（GMS2 同款）；不同纹理的绘制各自成段、保序即可。
- 不做场景图、绘制排序器、GPU 剔除等上游优化。
- 不改 GM8 资源模型（图集由 GMGraphic 现有 texture_atlas 提供，引擎未入图集的原生资源按独立段原样记录）。

## 3. 桥梁期：三件套——✅ 完成（2026-09-14 深夜）

> 本期三件互相独立、各自可单独实测与回退。它们同时是统一流的直接前置件：③ 的影子表被捕获器原样征用，① 的"自碰清单"是批段头机制的雏形。

### 3.1 修复②：去除批重开的大内存清零 ✅

**实施**（GMGraphic `49f3da4`）：`vertex::begin` 不再 memset 整缓冲（图集 192KB / ext 768KB）。历史靠 memset 恒零的字段改为写入方显式补齐：`push_vertex_2d` 写 z=0（ext 分支另补法线/高光 0，保 FFP 光照/镜面行为不变），2D 版 `draw_vertex_ext` 补 z/法线；`end()` 的 count+1 尾顶点改提交前单槽清零。语义收窄（已记档）：ext 格式下未写入的 uv stage 1-7 从"保证为 0"变为"未定义"，仅影响自定义 shader 采样未写通道（GMS2 同款契约）。

### 3.2 修复③：设备状态影子表 ✅

**实施**（GMDirectX9 `6304572`，版本 1.8）：新 `state_shadow.{h,cpp}`，43 槽钩内同步记账——渲染状态(0-255)/TSS(8×64)/采样器(16×16)/纹理(16)/变换族(0-257)/视口/FVF/顶点声明/VS/PS；设备创建与每次 Reset/重建成功后全量重播（SEH 自护，坏设备只降级为"未就绪"）。`SetVertexShader` 调用点包装与仿固定管线 WVP 刷新改读影子——消除每引擎绘制的 3 次 Get + 2 组 COM AddRef/Release 往返。读口经 `gmdx9_shadow_api` 单导出（v1 结构，只增不改），GMGraphic 与未来捕获器经 GetProcAddress 解析。**对账调试模式**：环境变量 `GMDX9_SHADOW_AUDIT=1`，每笔记账即时真 Get 逐项比对，差异写工作目录 `gmdx9_shadow_audit.log`（封顶 2000 行）。

【通俗地说】给设备的所有开关记一本账。以前每次想知道某个开关的状态都要跑去设备本人那里问一遍（还要签名登记）；现在翻自己的账本。这本账以后就是捕获器的唯一状态来源。

### 3.3 修复①：批冲刷最小自愈 ✅

**实施**（GMGraphic `49f3da4`）：`end_draw` 的三轮 38 项全量快照（≈114 次设备调用/flush）退役。默认路径 = **自碰清单**：end_draw 实际触碰的设备状态只有纹理 stage0-7、TSS0 的 ADDRESSU/V/COLOROP/COLORARG1/COLORARG2、PS/VS/声明/FVF——触碰前从影子读出（= 引擎现场），提交后按清单差异归还，典型整段仅 stage0 纹理一写。`start_draw` 的全量捕获同步移除。**调试对照**：环境变量 `GMGRAPHIC_BATCH_FULL_SNAPSHOT=1` 一键切回旧三轮路径；影子读口不可用（未装 GMDirectX9/旧版）自动落回。

**验收记录**：用户实测通过——计时器读数持平"恢复正常"基线，场景显示正常。影子对账零差异运行（总览待办第 2 项）与双模式截图比对（第 3 项）作为补充验收留在用户侧，不阻塞。

## 4. 统一流·阶段一：引擎绘制捕获器——⏸ 挂起

**启动门槛**：某场景计时器读数再次显著抬高（相对恢复后基线），或用户主动立项。

**技术描述**：

1. **捕获点唯一性**：8.0 引擎全部图元经 `DrawPrimitiveUP` 提交（全模块扫描核定，无 DrawPrimitive/IndexUP 站点），捕获面单一。
2. **段结构**：`{ 图元类型, 顶点数据副本(记录时 memcpy), 步长, 纹理(记录时 AddRef), 状态指纹(读影子表：FVF→声明映射、混合渲染态、TSS/采样、三矩阵、雾/Z 状态) }`。
3. **屏障类调用同队列**：`Clear`、`SetRenderTarget`、`SetDepthStencilSurface`、纹理内容更新（`UpdateTexture` 等）作为队列屏障记录，回放时原样执行——surface_set_target 与运行时烧图集天然保序。
4. **读回屏障**：`GetRenderTargetData`/`GetFrontBufferData`/锁定读回类操作触发"回放到此为止"，强制队列前段先落设备再执行读回。**[Q1 已定]** 第一版对读回函数绕过走旧路径（游戏内截图不进队列），回避最复杂时序。
5. **生命周期**：队列对纹理等 COM 对象记录时 AddRef、回放后 Release——`texture_swap`、运行时删除资源等边角自然正确。
6. **不合并**：第一阶段同状态相邻段不做合并（不同纹理的段各自独立提交，GMS2 同款常态），合并作为后续优化。

【通俗地说】引擎每次落笔不再直接上白板，而是被拍成一张"操作卡"（画了什么点、用什么笔、蘸什么颜色）按顺序码进盒子里。白板从此只有一个人能碰。

## 5. 统一流·阶段二：回放器——⏸ 挂起（依赖阶段一）

**技术描述**：

1. **回放点**：`EndScene` 钩子按调用序遍历队列：逐段应用状态 diff（对比前段指纹，只写变化项）、图集/SDF 段走现有提交代码（状态取自记录值，即批段头）、引擎段按记录状态提交。
2. **帧首确定性**：回放前将设备置入已知基准态，之后一切状态由队列主导——设备环境不再有"继承"概念。
3. **与既有机体的衔接**：gpart 的 RT ping-pong 即屏障序列，原样保序；设备丢失/Reset 时队列整体作废、下帧重录（挂接既有 reset 回调）；43 槽钩的 `fire_flush` 退役为"封段"（纯记账，零设备调用），冲刷风暴自机制上消失。
4. **影子表同步**：回放期间钩子照常维护影子（回放写入亦经 vtable），帧间一致性自动成立。

【通俗地说】帧尾由一个专职誊写员把盒子里的操作卡按顺序全部执行。因为整帧只有他碰白板，"画的时候白板是什么状态"不再是问题——每张卡自己写着呢。

## 6. 脚手架与收尾——⏸ 挂起（依赖阶段二）

- **模式开关**：GML 可调 `gmdx9_set_capture_mode(0/1)`（开发/验证期），一键在"现管线"与"统一流"间切换，用于截图对比、计时器对比、异常二分。**性质为带删除期限的脚手架，非永久特性**。
- **灰度**：以 gex 版本为单位（新版稳定跑一个版本 → 切默认），不做运行时灰度。
- **退役提交**：统一流默认并稳定后，专门一个提交删除旧提交路径，开关降级为无操作。用户侧回退手段 = 装回上一版 gex（文档明示），不以常驻双管线作保险。
- **[Q2 已定]** 旧提交路径删除时限：默认切换后 **1 个版本**。

（注：桥梁期已落地的两个环境变量 `GMDX9_SHADOW_AUDIT` / `GMGRAPHIC_BATCH_FULL_SNAPSHOT` 同属带删除期限的脚手架——影子对账零差异确认后前者可关；统一流落地后后者随旧快照路径一并退役。）

## 9. 明确不做

- 不实现绘制排序/合并率优化（第一阶段保序即可，合并留作后续纯增益项）。
- 不动 D3D8 后端（无 GMDirectX9 时的原生路径维持现状）。
- 不新增 GML 面向用户的图形语义（仅新增开发期模式开关一个导出，随旧路径一并退役）。
- 不在统一流落地前引入 D3D9 StateBlock（作为最小自愈的可选实现评估过，跨驱动质量参差，通用插件保守起见不采用）。
